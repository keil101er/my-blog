工程里通常叫**计数器回绕**，编码器里常说**角度跨零**。它们有同一个特点：**读数只告诉你现在位于这一圈的哪个位置。要知道两次读数之间走了多远，还需要知道方向，或者限制两次读数之间最多能走多远。**

### 1. 先看编码器：从 4090 变到 5，电机往哪边转了？

假设一个单圈编码器每转一圈有 4096 个计数，读数范围是 `0～4095`，正转时读数增加。实际的 12 位角度编码器就有这种表示方式。[ams OSRAM 编码器手册](https://look.ams-osram.com/m/d4566ea9c648455/original/AS5147U-AS5247U-DS000639.pdf)

你连续读了两次，上次是 `4090`，这次是 `5`。先看一条可能的运动路径：

```text
4090 → 4091 → 4092 → 4093 → 4094 → 4095 → 0 → 1 → 2 → 3 → 4 → 5
```

沿着这条路径数箭头，电机**正转了 11 个计数**。但如果代码直接做普通减法：

```c
int delta = 5 - 4090;  // -4085
```

得到的是反转 4085 个计数。**有意思的是，这个答案在物理上也可能成立。** 从 4090 反转 4085 格，最后同样停在 5。甚至正转 `4096 + 11 = 4107` 格，读数也还是 5。

所以，仅凭 `4090` 和 `5` 两个数，三种解释都说得通：

| 可能的真实运动 | 最后读数 |
|---|---:|
| 正转 11 格 | 5 |
| 反转 4085 格 | 5 |
| 正转一整圈，再正转 11 格 | 5 |

软件之所以敢选 **`+11`**，是因为我们能通过**电机最高转速和采样间隔**保证：这两次读取之间，电机最多只会转一小段。

### 2. 为什么经常用“半圈”作分界？

假设电机可以正反转，但你能保证**两次采样之间的实际转动小于半圈**。对 4096 格的编码器，半圈就是 2048 格。刚才三个候选位移里，只有 `+11` 满足这个条件，于是答案唯一。

这就得到了很常见的编码器代码：

```c
// previous 和 current 都是 0～4095 的单圈读数
int32_t delta = (int32_t)current - (int32_t)previous;

if (delta > 2048) {
    delta -= 4096;
} else if (delta < -2048) {
    delta += 4096;
}
```

拿两个方向各算一次，就能看懂为什么一边加、一边减：

| 上次 → 本次 | 直接相减 | 跨零修正 | 实际位移 |
|---|---:|---:|---:|
| `4090 → 5` | `-4085` | `-4085 + 4096` | 正转 11 格 |
| `5 → 4090` | `+4085` | `+4085 - 4096` | 反转 11 格 |
| `100 → 120` | `+20` | 无需修正 | 正转 20 格 |

**恰好半圈是分不出来的。** 比如 `0 → 2048`，正转 2048 格和反转 2048 格都会到达同一点。这也是为什么前提要说“**小于**半圈”。上面的代码并没有解决等于半圈的歧义，它依赖采样设计把这种情况排除掉。

### 3. 放到你的电机项目里，怎么知道采样够不够快？

假设**编码器所在的轴**最高转速是 `3000 rpm`。换算出来是：

- 每秒 `3000 ÷ 60 = 50` 圈。
- 一整圈需要 `20 ms`。
- 半圈需要 `10 ms`。

如果每 **1 ms** 收到一次新角度，轴在这段时间最多转 `0.05` 圈，也就是 `18°`，用上面的半圈规则很容易判断方向。

但是，假设 CAN 反馈中断了 **12 ms**，电机始终以这个速度正转。那么它实际正转了 `216°`。编码器只给你起点和终点，而**正转 216° 和反转 144° 的终点相同**。如果软件依然选择较短的那条路，就会把正转判断成反转。

这和你正在做的 PDO 网关有直接关系：**即使 EtherCAT 每 1 ms 交换一次 PDO，同一台电机的两条有效角度反馈也可能间隔更久。** 中间有空槽、反馈延迟或者丢帧时，计算位移要看两条**有效反馈**之间的实际间隔。连续跟踪单圈角度可以累计出相对多圈位置，但如果上电时只有一个单圈读数，之前一共转了多少圈通常无法由这个读数恢复。[ODrive 对单圈角度与多圈位置的说明](https://docs.odriverobotics.com/v/latest/manual/control.html)

### 4. 回到你的超时代码：为什么也是“半圈”？

你的代码是：

```c
now - deadline < (UINT64_C(1) << 63)
```

编码器的一圈是 `4096`，半圈是 `2048`；`uint64_t` 计数器的一圈是 `2⁶⁴`，半圈就是 `2⁶³`。**数学上用的是同一个分界，但你问的问题不同。**

- 编码器问：“从上次位置到本次位置，是向前走了一小段，还是向后走了一小段？”
- 超时判断问：“从截止时刻看，现在是刚过了它，还是还差一点才到它？”

这里还有一个容易忽略的区别：**并非所有计时器回绕计算都需要半圈规则。** 如果保存的是**开始时间**，而且知道计时器一直向前走，就可以直接算经过时间。拿 8 位计数器举例：

```c
uint8_t start = 250;
uint8_t now = 5;
uint8_t elapsed = (uint8_t)(now - start);  // 11 tick
```

只要实际经过时间**小于一整圈**，`11` 就是唯一答案，因为你已经知道时间只往前走。你的代码保存的是**截止时刻**，而 `now` 可能在截止时刻的前面，也可能在后面，所以才要用**半圈**来判断先后。Linux 内核也专门提供了处理计数器回绕的时间先后比较接口。[Linux 内核时间比较文档](https://docs.kernel.org/driver-api/basics.html)

所以，看见类似代码时，可以先问自己一句：**我是在算“已知向前走了多久”，还是在判断“两个位置谁在前、谁在后”？** 前者在一整圈内可以直接做无符号减法；后者在缺少其他方向信息时，通常需要半圈这个前提。
