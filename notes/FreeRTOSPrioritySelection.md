# FreeRTOS 优先级：通用查找与位图优化

**通用方法和架构优化方法，解决的都是“怎样找到最高的就绪优先级”。** 找到之后，再从该优先级的任务中选一个运行。

以下讨论单核 FreeRTOS。

## 优先级数量不等于任务数量

```c
#define configMAX_PRIORITIES 5
```

这表示可用优先级为 **0～4，数值越大，任务优先级越高**。它不是“最高优先级为 5”，也不是“最多创建 5 个任务”。多个任务可以使用同一个优先级。

假设 A 的优先级为 1、B 为 3，两者都就绪；C 的优先级为 4，但正在阻塞。调度器会选 B，因为 **C 还不能运行**。

## 通用方法：向下检查就绪列表

内核为每个优先级维护一个就绪列表。通用方法用 C 代码向下查找，直到遇到非空列表。

**实际实现会记录最高就绪优先级的信息，并从记录的位置开始检查，不是每次都从 `configMAX_PRIORITIES - 1` 完整扫描。** 若原来的高优先级列表变空，就可能需要继续向下找。实现见 [官方 `tasks.c` 的任务选择宏](https://github.com/FreeRTOS/FreeRTOS-Kernel/blob/main/tasks.c)。

可配置的优先级越多，最坏情况下可能检查的层数越多，每级就绪列表也占用 RAM。这里增加的是**查找开销和列表存储**，不是任务自身的业务执行时间。

## 架构优化：用位图表示哪些级别就绪

以 GCC 的 Cortex-M4F 端口为例，一个优先级对应位图中的一位：有就绪任务就置 1，没有就清 0。

```text
优先级： 4  3  2  1  0
位图：   0  1  0  1  1
```

最高的置位是第 3 位，因此最高就绪优先级为 3。第 0 位包含始终可运行的空闲任务。

该端口通过 `CLZ` 指令计算前导零数量，快速确定最高置位，不必逐级检查。**32 位位图最多表示 32 个优先级，即 0～31**。这是该端口实现的限制，不能直接当作所有 FreeRTOS 端口的统一上限。对应代码见 [官方 Cortex-M4F `portmacro.h`](https://github.com/FreeRTOS/FreeRTOS-Kernel/blob/main/portable/GCC/ARM_CM4F/portmacro.h)。

下面的配置值指 `configUSE_PORT_OPTIMISED_TASK_SELECTION`：

| 对比 | 通用方法 | 该 Cortex-M4F 优化实现 |
| --- | --- | --- |
| 配置值 | `0` | `1` |
| 查找方式 | 向下检查就绪列表 | 位图与 `CLZ` 指令 |
| 查找耗时 | 与需要跨过的空列表数量有关 | 查找最高位的指令耗时基本固定 |
| 级数限制 | 没有该位图带来的 32 级限制 | 最多 32 级 |

能否启用优化、未显式配置时默认用哪种方式，要看实际端口。不要把“未定义”一概理解成使用通用方法。

## 查找方式只影响响应速度

这个配置不决定高优先级任务能否抢占，也不决定同优先级任务是否按 tick 轮换。后两者分别由 `configUSE_PREEMPTION`、`configUSE_TIME_SLICING` 等配置影响。

**查找结果仍是当前运行任务时，可以继续执行，不一定发生任务切换。** 三个配置的分工要分开记：优先级有多少级、怎样找到最高就绪级、什么时候切换任务。
